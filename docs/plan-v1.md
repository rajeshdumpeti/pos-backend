# Plan v1 selected-date backend

Plan contract **1.0**, API `/api/v1`. Canonical endpoint:
`GET /api/v1/plan`. Operation ID: `get_plan_selected_date`. The supplied Milestone
2.C request is the approved implementation scope; no separate approved Plan file
or backend roadmap was found in the backend/governance checkout. This document
records implemented behavior. It does not broaden the product scope.

Exact TypeScript schemas, examples, UI integration and acceptance scenarios:
[frontend-plan-v1-handoff.md](frontend-plan-v1-handoff.md). Source contracts:
[plan_read_schemas.py](../app/api/plan_read_schemas.py), generated by
[main.py](../app/main.py) `create_app().openapi()` and served at `/openapi.json`.
OpenAPI includes `x-pos-plan-contract-version: 1.0`; Today retains its separate
`x-pos-today-contract-version: 1.0` and frozen response semantics.

## Architecture and authoritative facts

API route → `PlanSelectedDateService` → existing planning repository/UoW port ←
SQLAlchemy planning repository → PostgreSQL `plan_items`. The domain owns pure
classification, summary, ordering and insight. No Plan-owned duplicate item model
or table, new dependency, session creation in repositories, or commit on reads.
The UoW acquires/closes the session and translates persistence failures safely.
A single account/date SQL statement retrieves complete selected-date facts so
items, summary and insight share one statement's authoritative database state.
The clock is sampled once before the read; generated_at and freshness.as_of use
that same server UTC instant for all timing decisions.

Full-date facts are materialized, deduplicated and sorted in the application; the
response is bounded to at most 100 items. This deliberately simple v1 design
uses O(n) facts and O(n log n) sort for the selected day. It does not promise
bounded database work per page or snapshot consistency between requests. An SQL
aggregate/candidate/keyset optimization would need a separate measured change.

Existing index `(user_account_id, scheduled_for_date, scheduled_start_at)` has the
account/date equality prefix required by the new query. Sorting occurs in the
application, so no new state/order index is necessary. No schema or migration
change; head remains `0006_daily_planning`. Offline migration/model metadata
parity and guarded live parity/upgrade/downgrade tests remain the evidence paths.
No live parity claim is made when the guarded database is unavailable.

## Request, authorization and safe errors

Required selected_date is an exact `YYYY-MM-DD` valid date. Required timezone is
a valid IANA name. Optional limit defaults to 50, minimum 1, maximum 100. Optional
cursor is an opaque continuation from the previous response (bounded to 1024
characters). Unknown query fields, including account_id/user_account_id/client
`today`, are rejected. No account ID is accepted in query/body. Bearer session
authentication plus active account, verified email and completed authoritative
onboarding are reused unchanged. SQL predicates always use the authenticated
account and requested selected_date. Projection repeats those filters defensively.

Missing bearer/invalid/expired session → existing 401. Disabled/inactive account,
unverified email or incomplete onboarding → existing 403 gate codes. Invalid
date/timezone/limit/cursor/incompatible query → 422 `request_validation_failed`.
Repository/driver failure → 503 `dependency_unavailable`. Unexpected failures →
500 `internal_server_error`. All use the existing centralized SafeError with
request_id and safe details (empty for product validation). Raw cursor, payload,
SQL and exception text never appear in error responses. Retry 503/500 deliberately;
correct 422 input; use the existing auth recovery path for 401/403. Never substitute
an empty successful date for retrieval failure.

Every successful response has `Cache-Control: no-store`, `Pragma: no-cache` and
`X-Request-ID`; existing centralized errors preserve those headers as well.
Freshness is current-only; there is no offline freshness, stale threshold or sync.

## Explicit date ownership, travel and historical state

An item belongs to a date through durable scheduled_for_date, never by converting
scheduled_start_at in the requested zone. Travel does not rewrite assigned date,
stored timezone or absolute schedule instants. Requested timezone determines the
server's current local date, hence selected_date <, ==, > local_date means past,
current, future respectively. The item's stored timezone describes scheduling
intent for display; UTC start/end remain authoritative absolute instants.

Creation/update date, offset, end-after-start and DST rules are unchanged. Named
zone offsets must match each instant, start must match its assigned local date,
spring gaps reject and both valid fall folds accept their matching offsets. Plan
reads do not reinterpret or normalize persisted intent into another assigned day.

Past dates show **current authoritative state**. An item completed later is
currently completed and retains completed_at; an unfinished item is still
incomplete. Counts describe items currently assigned to this date. Neither API,
insight nor client may reconstruct a historical snapshot from these fields.

## Summary and deterministic sections

Deduplicate owned assigned item UUIDs across the complete date, independent of
page limit or cursor. Total is all assigned items; completed have non-null current
completed_at; remaining have null completed_at. Scheduled_remaining have a start;
unscheduled_remaining have none. Completed + remaining = total;
scheduled_remaining + unscheduled_remaining = remaining.

Completion percentage is equal-weight completed / total × 100, calculated with
Decimal and ROUND_HALF_UP to a whole integer. Zero total → null; 0/2 → genuine 0;
1/3 → 33; 1/8 → 13; 2/2 → 100. Priority, goals and unsupported measurements never
contribute additional weight.

| Section order | Within-section order |
| --- | --- |
| 1 scheduled_incomplete | scheduled_start_at ASC, UUID ASC |
| 2 unscheduled_incomplete | is_priority DESC, created_at ASC, UUID ASC |
| 3 completed | completed_at DESC, UUID ASC |

Priority never overrides scheduled timeline chronology. Every item returns the
original intent/audit/version fields plus section, timing_state and the sole
item action `plan_item.view`. Completed items leave both incomplete sections.
No persisted manual ordering exists.

## Cursor pagination

Page fields are limit, next_cursor and has_more. More results → cursor for the
last returned global ordering key. Final/empty page → next_cursor null, has_more
false. Traversing an unchanged dataset returns each UUID exactly once with no
gaps. Summary and insight always describe the entire selected date, even if the
recommended item is absent from the current page.

There was no existing cursor utility to reuse. Versioned canonical URL-safe
base64 JSON contains only an ordering key (bucket, priority rank, integer UTC
microsecond ordering value, UUID) and a SHA-256 query-context fingerprint.
The fingerprint binds the server-supplied authenticated account, selected date,
timezone and order version. It is **not a signature, encryption or authorization**.
No credentials, title, body, email or display name is encoded. Strict decoding
checks size, canonical form, field set/types, bounds, UUID and context. Cursor
validation happens before planning persistence access.

A well-formed manipulated key can change only the continuation position; it cannot
supply the account/date predicates or expose foreign records. Reusing a cursor
under a different account/date/timezone fails validation. Limit may change between
pages. Frontends must never decode, manufacture or depend on the encoding.

Each request sees current state. Inserts, edits, completion or date reassignment
between requests can move items across the anchor, changing traversal results.
No snapshot or historical guarantee is offered. After successful create, update
or complete, discard pagination and refetch the selected date from page one.
Refetch both affected dates after a date reassignment; refresh Today when relevant.

## Exact timing

| Current authoritative item | timing_state |
| --- | --- |
| completed_at non-null, any schedule | completed |
| incomplete with no start | unscheduled |
| incomplete with start > server now | upcoming |
| incomplete with start <= now < end, end exists | ongoing |
| incomplete with end <= now | past |
| incomplete point item with start <= now, no end | past |

Exact start with a future end is ongoing. Exact point start and exact end are past.
No grace period, departure/commute calculation or automatic optimization exists.
Timing uses absolute instants regardless of selected date relation; for example,
an interval assigned yesterday can still be ongoing across midnight. Past insight
still describes current incompleteness. The frontend must use supplied states.

## Deterministic Plan Insight

One recommendation, transparent reason, optional authoritative item UUID, one
supported action, and allow-listed evidence: selected_date, date_relation, total,
completed, remaining, is_priority, timing_state, scheduled_start_at. Evidence is
computed from the full date and selected item, never page-local or optimistic data.
Empty/complete/unavailable branches have null item-specific evidence.

Current precedence: ongoing priority, ongoing other, past incomplete priority,
past incomplete other, upcoming priority, upcoming other, unscheduled priority,
unscheduled other, all complete, empty. Same-category candidates use start ASC
(or unscheduled created_at ASC) then UUID ASC. Codes use current_ongoing[_priority],
current_past[_priority], current_upcoming[_priority], current_unscheduled[_priority].

Past precedence: incomplete scheduled priority, incomplete scheduled other,
incomplete unscheduled priority, incomplete unscheduled other, all currently
complete, empty. Codes past_remaining_priority/past_remaining; category still
respects scheduled before unscheduled. Reasons explicitly say still incomplete
or all/no items currently assigned to this date.

Future precedence: earliest incomplete scheduled priority, earliest incomplete
scheduled other, unscheduled priority, unscheduled other, all already completed,
empty. Codes future_scheduled[_priority], future_unscheduled[_priority]. Schedule
or creation then UUID resolves ties. No outcome or benefit is predicted.

All-complete → selected_date_complete, available, create action, no item ID.
Empty → selected_date_empty, empty, create action, no item ID. Item selection →
available, view action, real item ID. Only plan_item.create/plan_item.view are
advertised; destinations belong to the frontend.

The shared pure selector in `app/domain/plan_selection.py` preserves Today's
frozen six past-start/upcoming/unscheduled tiers. Plan explicitly opts into eight
tiers to distinguish ongoing. Today still uses its existing past-start wording,
score, priorities, Up Next and Wins; its response and contract are unchanged.

## Insight isolation and diagnostics

Insight uses a cohesive pure builder with an injectable application boundary.
Only deliberately modeled InsightComputationError is caught. On that failure,
items and summary remain usable; insight state unavailable, code
insight_unavailable, generic copy, null action and item ID, full-date evidence.
Repository failures remain global safe 503; arbitrary unexpected errors remain
safe 500. No general exception catch hides persistence or programming failures.

Existing safe structured planning diagnostics accept plan_selected_date_read and
plan_insight_unavailable, bounded request ID, account UUID, null item UUID, version
0 and fixed outcome. No cursor, title/body, email, tokens, URL, SQL or exception
text is recorded. Unavailable insight emits the fixed unavailable outcome.

## Compatibility, delivered and deferred capabilities

Existing POST/GET/PATCH/complete item endpoints and GET Today are preserved.
Idempotent create receipts/hash/replay, optimistic expected_version, increments,
completed-item edit rejection, completion replay, safe foreign 404, gates and
cache behavior remain unchanged. See [Today contract](today-dashboard.md).

Delivered: selected-date authoritative read, sections/timing, bounded cursor
response, full-date summary, deterministic insight and isolated modeled failure.
Deferred: recurrence/repeating tasks, subtasks, drag/manual order, automatic
scheduling, providers/calendar sync, all nutrition/workout/health/money/focus
measurement stores, offline mutation queues/sync, historical snapshots/event
sourcing, AI/predictions/confidence/benefits/personalization, frontend work and
deployment. No new mutation or unsupported action was added.

## Swagger and founder manual verification

Prerequisites: reviewed checkout/delivery SHA, maintained IANA timezone database,
secure existing authentication/session/onboarding configuration and an authorized
test environment with migration 0006. Never paste credentials or tokens into
reports. Destructive automated tests require local pos_test via guarded
POS_TEST_DATABASE_URL; they never inspect .env or clean a development database.

1. Inspect `/openapi.json` and `/docs`: one selected-date operation, Plan 1.0,
   named closed responses, required date/zone, limit 50/100, Bearer, safe errors.
2. Register, verify email, sign in and complete onboarding with existing flows;
   authorize privately in Swagger. Retrieve an empty selected date: null percentage,
   empty insight and current freshness/cache/request-ID headers.
3. Create scheduled and unscheduled items, with priorities and tied starts. Read
   with limit=1 and traverse all pages. Verify chronology and priority rules, full
   summary and insight even when the recommendation is not on the page.
4. Test invalid date/zone/limit/cursor, unknown account input, cursor reused for
   another date/zone/account: safe 422 with no raw supplied value.
5. Check current/past/future dates. Complete an older assigned item today and
   refetch: currently completed, visible later completed_at, no historical claim.
6. Check exact interval start/end, point start, local midnight, travel, DST gap
   rejection and both folds through existing item mutations.
7. Create/replay/update/stale conflict/complete/replay using existing contracts;
   discard the cursor and refetch page one. Compare Today before/after Plan reads.
8. Use a second account, unverified/inactive accounts and incomplete onboarding.
   Verify no foreign data, existing 401/403 gates and foreign item 404.
9. Inject modeled insight failure only in a controlled test: items/summary remain.
   Simulate repository outage separately: safe global 503, never fake empty data.
10. Against guarded disposable pos_test only, run planning/selected-date PostgreSQL
    tests and existing migration parity/upgrade/downgrade/cascade tests. Offline SQL
    alone is not evidence of live PostgreSQL behavior.
